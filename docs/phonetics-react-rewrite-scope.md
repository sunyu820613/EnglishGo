## 0. 背景与已核实事实

本文档基于对以下文件的实际读取核实（非假设）：

- `pubspec.yaml`：现有 Flutter 依赖含 `just_audio`（三通道音频）、`go_router`、`flutter_riverpod`、`shared_preferences`；无任何语音识别/评分相关依赖。
- `assets/data/alphabet.json`：26 个字母条目，每个含 `letterAudio`（字母名读音）、`phonicsAudio`（拼读音）、`phonicsIpa`（拼读音 IPA 符号）、2 个例词（含 `audio`/`image`/`phrase` 三个音频+图片字段）。**没有字母名的 IPA 字段**（只有拼读音 IPA），如果要做“字母名 IPA vs 拼读音 IPA”对比展示，字母名 IPA 需要新增数据。
- `lib/features/phonetics/phonetics_chart_page.dart`：现有的音位图表原型。核实其音位清单固定为 **47 个**符号（元音 10 + 双元音 5 + 儿化元音 6 + 清辅音 8 + 浊辅音 8 + 其余辅音 10），每个音位对应 1 个发音文件 + 最多 3 个例词。该页面**没有**男女声切换、正常/慢速切换、嘴型动画、口腔剖面动画、最小对立音对比、录音评分 — 只是"点击符号播放一次录音 + 看 3 个例词"的静态图表，只能作为交互参考，不能直接迁移。
- `lib/core/audio/audio_service.dart`：语音/音效/BGM 三通道播放器，核心规则：新语音自动打断旧语音、BGM 播放语音时闪避到 20% 音量、静默降级（文件缺失只打印警告不崩溃）。这套规则在 Web 版应保留（用 Web Audio API 或 `<audio>` 元素重实现）。
- `lib/core/theme/tokens.dart`：间距（4/8 网格）、圆角、双层软陶土阴影、触控尺寸（最小 48px / 儿童 64px / 主操作 88px）、字体族（Baloo2 展示/Nunito 正文/Andika 教学）、字号阶、动效时长与缓动曲线、层级。这是"精品绘本感"视觉语言的量化基线。
- 音频/图片资产实际清点：
  - `assets/audio/letters/`：26 字母名（`{x}_name.m4a`）+ 26 拼读音（`{x}_phonics.m4a`，无男女区分）+ `male/`、`female/` 子目录各 26 个字母名录音（`letter_{x}_male/female.ogg`），共 104 个男女分离文件。
  - `assets/audio/phonemes/`：50 个 `.wav` 文件，其中 47 个对应 `phonemeAudioSlugs` 映射表中的合法音位 slug（如 `iː→i`, `æ→ae`），另有 **3 个明显的测试遗留文件** `_male_b_test.wav` / `_male_d_test.wav` / `_male_g_test.wav`（无男女声完整体系，只是三个测试样本，命名暗示"未来想做男女声但目前没做"）。**当前音位音频不分男女声、不分正常/慢速**，每个音位只有 1 个音频文件。
  - `assets/audio/example_words/`：114 个例词发音文件，命名为纯单词（如 `see.m4a`），与 `phoneme_example_words.dart` 中约 3 词/音位 × 47 音位（部分复用）对应。
  - `assets/audio/words/`、`assets/audio/phrases/`：字母学习用的单词发音与"A is for Apple"短句发音（从 alphabet.json 引用，未单独清点但结构与 letters 一致，52 词 × 2 文件）。
  - `assets/images/words/`：52 张单词插画（webp），对应 26 字母 × 2 词。
  - **没有**任何嘴型/口腔剖面动画素材（图片/SVG/Lottie/视频）。
- `lib/core/content/phoneme_audio_slugs.dart` / `phoneme_example_words.dart`：确认音位符号→ASCII slug 映射表已存在且可直接复用为数据源（避免 Web 端 IPA 文件名 URL 双重编码 404 的坑，新项目应延续 ASCII slug 命名约定）。

结论：现有素材能完整支撑**字母学习 + Phonics 教学 + 47 个音位的"文字+音频+例词"层**，但**动画层（嘴型/口腔剖面）、男女声/正常慢速的音位音频矩阵、最小对立音对比、录音评分**全部是从零开始的新工作，没有可复用素材。

- **不做**任何原生打包（无 Capacitor/Electron/iOS/Android 壳）。

## 2. 里程碑拆分

### M1 — 项目骨架 + 字母学习 + Phonics 迁移
**内容**：Vite+React+TS 项目初始化、路由、设计 token 体系（CSS 变量/Tailwind）、音频播放服务（三通道规则移植）、字母学习 26 页（字母名+拼读音+男女声+2 例词）、本地进度持久化基础（学过哪些字母）。
**产出**：可在手机/平板浏览器访问的字母学习闭环，视觉质感对标原 Flutter 版。

### M2 — 5 个样板音素完整实现（验证动画与音画同步方案）
**内容**：选 5 个有代表性的音位（如 /iː/ /æ/ /θ/ /r/ /ŋ/，覆盖元音/擦音/近音/鼻音），做出音位学习页完整功能：IPA 符号、正常/慢速播放、男/女声切换、正面嘴型动画、侧面口腔剖面动画、例词、最小对立音对比（每音位至少 1 组对比）。此阶段用于验证动画技术方案（SVG 帧动画/Lottie/视频）与音频-动画同步机制，供后续 40+ 音位复用同一套组件与流水线。
**产出**：5 个音位页面可交付演示，技术方案（动画格式、同步机制、音频命名规范扩展）书面确认。

### M3 — 全量 47 音位扩展
**内容**：按 M2 验证的方案，产出全部 47 个音位的完整素材（音频矩阵 + 双动画）与页面内容（例词、对立音对），接入音位总览图表页（对标旧 `PhoneticsChartPage` 但功能完整版）。
**产出**：47/47 音位内容完整可学习。

### M4 — 录音评分 + 收藏/进度完善
**内容**：录音 UI、（若 Key 到位）Azure Pronunciation Assessment 接入或（若未到位）mock/回放对比降级方案、收藏音位/字母、"最近学习"列表、学习进度可视化。
**产出**：完整学习闭环含个性化数据，具备正式发布条件。

## 4. 已知阻塞项（需用户提供才能继续）

1. **Azure Speech Key + Region**（最大阻塞项）：M4 的自动发音评分功能依赖 Azure Pronunciation Assessment API。当前环境变量 `SPEECH_KEY`/`SPEECH_REGION` 未设置。若不提供，M4 按 3.1 中的降级方案（仅录音回放，无自动打分）交付，不阻塞 M1-M3。
2. **是否需要后端代理**：Azure Speech Key 不能直接暴露在前端（会被用户看到/滥用配额）。若做真实评分，需要一个轻量后端（Node/Serverless 均可）做 Key 代理。**需要用户确认**：是否愿意维护一个最小后端服务/云函数，还是接受"仅录音无评分"的纯静态方案。
3. **动画制作资源**：正面嘴型动画 + 侧面口腔剖面动画（含舌位/软腭/气流/声带振动状态）共 47 套 × 2 视角，是全新美术/动画工作量，**当前无该类素材、无制作该素材的现成工具链**。需要用户明确：动画由谁制作（外包/AI 生成工具/内部美术）、采用什么格式（SVG 帧序列/Lottie/视频），这直接决定 M2 的技术方案选型。
4. **字母名 IPA 数据**：`alphabet.json` 目前只有拼读音 IPA，字母名 IPA（如 A 的 /eɪ/）需要新增约 26 条数据，工作量小但需要人工/语音学核对，非技术阻塞，仅提示需补数据。
5. **音位对立音对内容**：最小对立音对（如 /iː/-/ɪ/ ship/sheep）的具体配对表尚不存在，需要内容设计（可由内容团队或 AI 辅助生成，但需人工审核，避免不适合 3-6 岁语境的词）。

## 总结（供项目经理链路使用）

本文档核实了现有 Flutter 项目的真实资产（26 字母×2 词音频/图片齐全、47 个音位仅有单一版本音频且无任何嘴型/口腔动画素材、无录音评分基础设施）后，将用户诉求拆分为 4 个里程碑：M1 骨架+字母/Phonics 迁移、M2 五音位样板验证动画方案、M3 全量 47 音位扩展、M4 录音评分与个性化数据。每个里程碑给出可核查验收项（非"做完了"式模糊标准）。关键决策点：(1) 动画制作方式未定，是 M2 最大技术风险；(2) Azure Speech Key 缺失，评分功能设计为可插拔降级，不阻塞主线；(3) 47 个音位音频均需补录男女声+慢速版本，现有音频只能作为"正常速单声线"过渡资产；(4) 六主题系统是否保留、评分后端是否搭建，均需用户明确回答后才能定 M1/M4 技术方案。文档已写入 `D:\AI\EnglishGo\docs\phonetics-react-rewrite-scope.md`，建议下一步由 architect 基于本文档做技术方案设计（尤其 M2 的动画同步机制选型），frontend-designer 跟进视觉系统重建。
